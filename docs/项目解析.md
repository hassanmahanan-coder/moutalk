## 谈判引擎状态机（流程）

**1、意图分析**

将用户的问题通过模型结构化，提取用户意图（报价/拒绝/询问/让步）、价格等信息。

**2、战术选择**

分析后的结果通过设定好的规则引擎考虑使用8种战术中的哪一种战术进行回答，如果战术都未命中则让LLM兜底选

（红脸白脸、时间压迫、最后通牒、虚假底线、分而治之、沉默施压、让步诱饵、信息不对称）。

**3、话术生成**

通过上面两步结果调用大模型生成第一版回答。

**4、底线检查**

先不将回答直接发给用户，要对回答进行底线检查，检查是否超出底价或者高出上限等问题，如果超出底线设置则通过条件路由回到话术生成节点重新生成话术（其中携带了重试原因提示大模型出现的问题），然后再查，最多重试3次，最后再不行则使用兜底话术。

**5、兜底回退**

如果突破底线则自动选择重新调动大模型进行回答或者走兜底话术



**LangGraph起到的作用**

LangGraph的StateGraph用共享状态（字典）驱动五个节点（因为每个节点不会互相传话，所以统一读或者写共享状态state就可以知道上一步的决策）、用条件边表达底线检查的三分支重试回路（是否输出结果、是否重试、是否使用兜底话术），并通过Checkpoint把每轮状态写给PostgreSaver支持断点续谈。



## 谈判记忆型RAG（在话术生成节点使用，制作参考资料供使用）

**向量化、存入向量库、查询与检索、上下文增强（格式化检索内容）、生成话术**



每轮对话结束之后（问完后回答）将用户的问题和对手回复向量化，再存入向量库Milvus中；在生成话术节点开头，先将向量化的用户问题做余弦相似搜索，查找“历史类似场景的相关回答”，在Milvus向量库中通过粗粒度排序取top-10的内容再进行（Reranker）精排截取top-3，格式化后拼接进prompt中调用大模型生成话术。

**问题1（检索）：**在新场景中没有历史记录时，直接不检索当前用户问题调用大模型进行回答；当有历史记录时，先通过粗粒度检索top10的对手回答，直接将用户问题排除在外，防止大模型用用户问题作为参考答案来回答，然后再通过重排（精排）top3的检索内容，将检索内容拼接到prompt中调用大模型进行回答。

**问题2（检索）：**embedding是通过语义检索来进行向量化的，Milvus先按filter过滤圈定候选集，将用户问题移除，只保留对手回答，再通过余弦距离粗召回top-10；然后再通过Reranker将当前用户问题+top-10拼接为十队数据进行打分重排，将top-3提取出来注入到prompt。

**问题3（模型降级）：**当Milvus连接不上、BGE模型加载失败、检索为空时，直接跳过历史参考直接使用原样prompt继续进行。





## Saver存档

State是一个大字典，每单个节点走完就存入到State中，下一个节点运行完将状态的值覆盖对应键里的值，然后将State整体拷贝持久化到Postgres的Checkpoints表中；当断线续连时将会拿到最近入库的State，里面包含之前存入的所有节点的状态，而不是单独的一个节点状态。



**问题1（断点续传）：**断点续谈则是通过心跳机制来判断，前端每30s发一次ping，后端如果没接收到ping则判断连接断开，前端收到连接断开的消息进行指数退避重连（1s、2s、4s、8s、16s、30s，2*n重连，最高30s重试）；

在断开连接时对手的回复则进入到Redis缓存中，因为后端每次调用大模型回答的内容都先写进Redis中再发送给前端，前端收到信息后会回复{type: ‘ack’}，后端才将当前结果的缓存进行清空，以便接受下一轮用于回答的结果。

因为每次后端发送的消息传入前端后，前端都会回复ack，而在前端回复ack之前就断联，这时的内容都是还存放在Redis中缓存的，所以连接成功后前端会发送resume到后端，后端取出所有未ack的轮次打包发送给前端。

所有的会话状态都是从PostgreSaver中读取的，报价曲线、轮次、历史全部进行还原。



## Celery异步生成报告

**问题1（为什么异步）：**复盘报告需要LLM主观评分+分数聚合+PDF导出，如果在用户点击谈判结束后同步生成报告的话就会让用户再等十几秒才退出，导致体验感不好。所以必须让谈判快速收尾，复盘报告丢给后台慢慢结算最后再通知。

异步生成报告的流程：用户点击谈判结束后，WebSocket发送消息到后端，后端同步返回简单的结果，紧接着API把任务投进Redis队列中，worker从队列中取任务生成报告，生成完后落库（存入*notifications*表中）再经过Redis事件总线通知API进程，API再推送给用户,PDF子任务导出pdf_url，前端推送。

降级处理：当Celery本机未安装或者未开启或者未连接上时，直接降级未同步生成。

**问题2（如何传入前端）：**因为worker和API是两个独立的进程，worker并没有WebSocket功能，所以跨进程用Redis的发布/订阅功能。

传入前端流程：当worker的报告生成完成后，创建发布事件同步到队列中，然后让API进程常驻订阅该队列，收到事件后通过WebSocket将信息传入到前端，前端收到信息后跳转到报告页即可看到

关键的是“双写”策略：先落库再实时推送（如果用户不在线先存入前端的通知表中，用户在线立即收到通知），当报告完成后再当前谈判的WebSocket连接直发一条“报告已生成”的消息，前端收到直接跳转到详情页。

如果WebSocket连接断开则会启动“轮询兜底”，Roomview的pollReport将会轮询报告列表重试15次，弹窗提示“报告生成中”

**WebSocket推送是加速生成，轮询是兜底，保证用户一定能拿到报告**

*结束谈判 → 后端同步返回 simple_result → API 把报告任务投进 Celery 队列 → worker 消费：读会话数据、算客观分、LLM 算主观分（失败置空）、0.6/0.4 聚合落库 reports 表 → 双写通知（落库 notifications 表 + Redis 事件总线发事件）→ API 进程订阅到后 WS 推给用户 → PDF 子任务导出 pdf_url → 前端推送加速、轮询兜底。异步保体验、双写防丢、事件总线打通跨进程。*



## Redis（按照角色设计不同降级处理）

1. **Celery任务队列：**报告生成、PDF导出的任务排队；worker使用Redis的BRPOP命令阻塞取任务（弹出队列最后一个元素，没有元素则阻塞队列）；
2. **断线缓冲：**断线期间完成的轮次存起来，重连后从最新存起来的轮次开始；
3. **事件总线：**发布pub/订阅sub，用于两个进程连通（worker->API进程跨进程通知）
4. **LLm限流：**单用户LLM调用5次/分钟，每次调用大模型前检查限流次数，超限降级话术
5. **会话并发锁：**防止同一会话的WebSocket并发调用（连点/双击时第二条信息429）
6. **趋势缓存：**报告进步曲线1小时缓存

每个角色都不会因为功能损失而导致谈判失败，每个都有降级处理，但是每个降级之后的损失各不相同

队列连不上降级为同步生成报告，导致谈判变慢；

断线缓冲写入异常跳过，导致回放丢失；

发布失败导致在线通知功能丢失，靠落库通知保底；

限流异常导致持续烧钱；

并发锁异常导致保护失效，可能会重复处理同一个事务；

趋势缓存异常导致出图速度变慢。



## 教练（coach）

前端按“教练”按钮，WS发送{type:"coach"}，后端接收到coach，创建教练的prompt（当前轮次+最近6条对话历史+已用战术+出价记录+教练视角），调用大模型输出3个话术通过WS推送给前端，生成失败则降级，按照无LLM key的三套模版判断输出话术；前端选择其中一个话术则直接填入输入框发送出去，对手正常处理问题（意图分析-战术选择-话术生成-底线检查-兜底）





## 总结

因为项目是*前后端分离模式*，用户在前端通过WebSocket发送消息，后端驱动基于LangGraph的这5个节点状态机，让大模型流式生成回复到前端（流式输出通过调用大模型输出第一版回答的内容，然后进行底线检查，最后再输出确认好的结果）；

每轮谈话结束后，会话状态通过PostgreSaver持久化到PostgreSQL，支持断线重连；对话内容向量化存入Milvus。

下一轮谈判开启时调用RAG检索相关历史注入到上下文；

复盘报告由Celery异步生成，完成后通过Redis缓存推送到用户的前端界面。
